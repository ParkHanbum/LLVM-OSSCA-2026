▸ LLVM은 소스 코드를 프론트엔드(Clang)에서 LLVM IR로 바꾼 뒤, opt이라는 미들엔드 최적화 파이프라인을 거쳐, 마지막으로 llc라는 백엔드를 거쳐 어셈블리를 만듭니다.

▸ InstCombine은 이 미들엔드 파이프라인 안에서 동작하는 정규화 패스로, 원본 IR과 의미적으로 완전히 동일하지만 더 간단한 형태의 IR로 명령어를 계속 재작성(rewrite)합니다.

▸ 이 패스는 -O1 이상에서 항상 실행되며, opt -passes=instcombine 명령으로 단독 실행해 효과를 직접 확인할 수 있습니다. 이 위치 관계를 기억해두면, 잠시 후 나올 '왜 이슈가 한 번 잘못 닫혔는가' 이야기가 바로 이해됩니다.

ISSUE #98800 / Alive2가 찾아낸 누락된 최적화

ISSUE #98800

Alive2가 찾아낸 누락된 최적화

alive2.llvm.org — @src ≡ @tgt (증명됨)
define i32 @src(i32 %a, i32 %b, i1 %c1, i1 %c2) {
  %sel1 = select i1 %c1, i32 %a, i32 %b
  %sel2 = select i1 %c1, i32 %b, i32 %a
  %ret  = select i1 %c2, i32 %sel1, i32 %sel2
  ret i32 %ret
}

define i32 @tgt(i32 %a, i32 %b, i1 %c1, i1 %c2) {
  %xor = xor i1 %c1, %c2
  %ret = select i1 %xor, i32 %b, i32 %a
  ret i32 %ret
}

▸ 제보자는 Alive2(형식 검증 도구) 증명 링크 하나만 남겼습니다.

▸ c1으로 a,b를 고르는 select와 정확히 반대로 고르는 select를 다시 c2로 고르는 구조는, c1과 c2를 xor한 값으로 바로 a 또는 b를 고르는 것과 완전히 동일합니다.

▸ select 3개짜리 구조를 xor 1개 + select 1개로 줄일 수 있는데, InstCombine이 이를 놓치고 있었습니다.

PATTERN MATCH / IR 구조를 매칭하는 방법: PatternMatch

PATTERN MATCH

IR 구조를 매칭하는 방법: PatternMatch

OuterSel = select(OuterCond, TrueArm, FalseArm)

TrueArm =

select(InnerCond, X, Y)

FalseArm =

select(InnerCond, Y, X) ← m_Deferred

두 InnerCond는 반드시 동일한 SSA 값이어야 매칭 성공 (m_Deferred)

▸ m_Select(Cond, True, False) — select 구조 자체를 매칭합니다.

▸ m_Value(X) — 매칭된 값을 변수 X에 바인딩합니다.

▸ m_Deferred(X) — '앞서 m_Value로 담아둔 값과 정말로 같은 SSA 값'이어야만 매칭에 성공합니다. 이름이 같은 게 아니라 포인터 수준에서 동일한 값이어야 합니다.

▸ 이 제약 때문에 안쪽 두 select의 조건은 리터럴로 완전히 같은 하나의 값이어야만 이 폴드가 작동하며, 이는 뒤에 나올 '스코프를 넓히지 않기로 한 결정'과도 직결됩니다.

▸ 리뷰어 dtcxzyw가 제시한 반례: 안쪽 select는 레인별 벡터 조건, 바깥 select는 스칼라 조건 — 둘 다 LLVM IR에서 유효한 조합입니다.

REVIEW FINDING ② / 리뷰가 찾아낸 문제 ② — 손해 보는 최적화

REVIEW FINDING ②

리뷰가 찾아낸 문제 ② — 손해 보는 최적화

원래 코드 (3개 명령어)

무조건 폴드 적용 시 (5개 명령어)

sel1 = select c1, a, b   (다른 곳에서도 사용)
sel2 = select c1, b, a   (다른 곳에서도 사용)
ret  = select c2, sel1, sel2
sel1 = select c1, a, b   ← 여전히 필요(외부 사용)
sel2 = select c1, b, a   ← 여전히 필요(외부 사용)
xor  = xor c1, c2   ← 신규
ret  = select xor, b, a  ← 신규

▲ +2 명령어

▸ 리뷰어 nikic의 지적: 안쪽 두 select가 각각 다른 곳에서도 이미 쓰이고 있다면, 폴드를 적용해도 원래 sel1·sel2는 사라지지 않고 그대로 남아야 합니다.

핵심 원리와 편집 주석

변환

LLVM
; Before
%s1 = select i1 %c1, i32 %a, i32 %b
%s2 = select i1 %c1, i32 %b, i32 %a
%r = select i1 %c2, i32 %s1, i32 %s2

; After
%x = xor i1 %c1, %c2
%r = select i1 %x, i32 %b, i32 %a

안쪽 두 select는 같은 조건과 반대 순서의 값을 사용한다. 바깥 선택까지 합치면 조건 두 개의 XOR로 최종 값을 고를 수 있다.

검증 도구의 범위

이슈는 처음에 코드 생성 이득이 없다는 이유로 닫혔다가 다시 열렸다. 최초 확인은 InstCombine을 실행하지 않은 llc 비교였다.

SH
opt -passes=instcombine -S input.ll -o combined.ll
llc combined.ll -o output.s

검증하려는 패스를 실행하지 않으면 해당 최적화의 유무를 판단할 수 없다. IR 변화와 기계어 변화를 순서대로 확인한다.

리뷰에서 추가한 조건

  • 안쪽과 바깥쪽 조건의 타입이 같아야 한다.
  • 두 안쪽 select는 각각 바깥 select에서만 사용되어야 한다.
  • 같은 조건과 반대 순서의 같은 SSA 값인지 확인한다.

조건 타입이 다르면 XOR 생성에서 크래시가 날 수 있다. 안쪽 select가 다른 곳에서도 필요하면 새 XOR 비용만 추가되고 기존 select가 남을 수 있다.

읽을 때 확인할 점원자료에는 multi-use 뒤 명령어 수를 5개로 센 설명이 있다. 바깥 select를 새 select로 대체하는 순수 명령어 집계는 4개다. 핵심은 3개에서 늘어날 수 있다는 점이다.

검증과 범위 결정

자료는 기본형, 피연산자 순서, scalar·vector 조합, multi-use, 조건 타입 불일치를 포함한 9종 회귀 테스트를 정리한다.

반대 조건으로 확장하는 안과 scalar 조건을 vector로 넓히는 안은 사용 빈도와 검증 결과를 근거로 보류했다. 이미 병합된 PR의 리뷰 과정을 분석한 자료다.
