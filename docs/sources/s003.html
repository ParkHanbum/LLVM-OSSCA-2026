InstCombine foldClampWithNaNFallback 패치 보고서

clamp-with-NaN-fallback 패턴을 minnum/maxnum 정규 형태로 접는 InstCombine fold 추가 브랜치: experiment/clamp-nan-fold · 파일: llvm/lib/Transforms/InstCombine/InstCombineSelect.cpp (+80줄)

1. 요약

여러 개의 fcmp + select로 손으로 쓴 "clamp(값을 [LO, HI]로 자르되 NaN이면 fallback)" 패턴을, LLVM의 표준 부동소수점 intrinsic(llvm.minnum / llvm.maxnum) + 단일 select로 정규화(canonicalize) 하는 최적화를 InstCombineSelect.cpp에 추가했다.

  • 위치: InstCombinerImpl::visitSelectInst 내부 (마지막 return nullptr; 직전 훅)
  • 헬퍼 함수: foldClampWithNaNFallback (InstCombineSelect.cpp:4488)
  • 검증: 기능 테스트(POS) + 오탐 대조군 6종(N1~N6) + InstCombine 전체 회귀 1750/1750 통과

2. 무엇을 바꿨나 (배치 / BEFORE → AFTER)

visitSelectInst는 InstCombine이 모든 select 명령을 방문할 때 호출된다. 기존 fold들이 전부 실패한 맨 끝에 우리 훅을 걸어, 다른 최적화를 방해하지 않도록 했다.

2-2. IR 변환 BEFORE → AFTER

BEFORE — 입력 IR (fcmp 3개 + select 3개, 총 6개 연산):

%below_lo_or_nan = fcmp nsz ult float %x, 0.0
%below_hi        = fcmp nsz olt float %x, 1.0
%upper           = select nsz i1 %below_hi, float %x, float 1.0
%ordered         = fcmp ord float %x, 0.0
%lower_or_fb     = select nsz i1 %ordered, float 0.0, float %fallback
%result          = select nsz i1 %below_lo_or_nan, float %lower_or_fb, float %upper

AFTER — fold가 생성한 정규 형태:

%isnan   = fcmp uno float %x, 0.0
%1       = call nsz float @llvm.minnum.f32(float %x, float 1.0)   ; 상한 clamp
%2       = call nsz float @llvm.maxnum.f32(float %1, float 0.0)   ; 하한 clamp
%result  = select i1 %isnan, float %fallback, float %2

의미: x가 NaN이면 fallback, 아니면 x를 [LO, HI]로 자른 값.

2-3. 패치 diff (핵심 발췌)

// [추가] 헬퍼 함수 — 패턴 매칭 후 정규 형태 생성
static Value *foldClampWithNaNFallback(SelectInst &Outer,
                                       InstCombiner::BuilderTy &Builder) {
  Value *BelowLoOrNan, *LowerOrFallback, *Upper;

  // Outer: select nsz belowLoOrNan, lowerOrFallback, upper
  // ★ hasNoSignedZeros()는 FP 연산에서만 유효 → 정수 select는 먼저 배제
  if (!isa<FPMathOperator>(&Outer) || !Outer.hasNoSignedZeros())
    return nullptr;
  if (!match(&Outer, m_Select(m_Value(BelowLoOrNan), m_Value(LowerOrFallback),
                              m_Value(Upper))))
    return nullptr;

  // belowLoOrNan: fcmp nsz ult %x, LO
  auto *Cmp1 = dyn_cast<FCmpInst>(BelowLoOrNan);
  if (!Cmp1 || Cmp1->getPredicate() != FCmpInst::FCMP_ULT ||
      !Cmp1->hasNoSignedZeros())
    return nullptr;
  Value *X = Cmp1->getOperand(0);
  auto *Lo = dyn_cast<Constant>(Cmp1->getOperand(1));
  if (!Lo)
    return nullptr;

  // upper: select nsz (fcmp nsz olt %x, HI), %x, HI
  auto *UpperSel = dyn_cast<SelectInst>(Upper);
  if (!UpperSel || !UpperSel->hasNoSignedZeros())
    return nullptr;
  auto *Cmp2 = dyn_cast<FCmpInst>(UpperSel->getCondition());
  if (!Cmp2 || Cmp2->getPredicate() != FCmpInst::FCMP_OLT ||
      !Cmp2->hasNoSignedZeros() || Cmp2->getOperand(0) != X)
    return nullptr;
  auto *Hi = dyn_cast<Constant>(Cmp2->getOperand(1));
  if (!Hi || UpperSel->getTrueValue() != X || UpperSel->getFalseValue() != Hi)
    return nullptr;

  // lowerOrFallback: select nsz (fcmp ord %x, *), LO, %fallback
  auto *LowSel = dyn_cast<SelectInst>(LowerOrFallback);
  if (!LowSel || !LowSel->hasNoSignedZeros())
    return nullptr;
  auto *Cmp3 = dyn_cast<FCmpInst>(LowSel->getCondition());
  if (!Cmp3 || Cmp3->getPredicate() != FCmpInst::FCMP_ORD ||
      Cmp3->getOperand(0) != X)
    return nullptr;
  if (LowSel->getTrueValue() != Lo)
    return nullptr;
  Value *Fallback = LowSel->getFalseValue();

  // 매칭 성공 → 정규 형태 생성
  Value *IsNaN = Builder.CreateFCmpUNO(X, X, "isnan");
  Value *UpperV = Builder.CreateBinaryIntrinsic(Intrinsic::minnum, X, Hi);
  cast<Instruction>(UpperV)->setHasNoSignedZeros(true);
  Value *Clamped = Builder.CreateBinaryIntrinsic(Intrinsic::maxnum, UpperV, Lo);
  cast<Instruction>(Clamped)->setHasNoSignedZeros(true);
  return Builder.CreateSelect(IsNaN, Fallback, Clamped, "clamp.or.fallback");
}

// [추가] visitSelectInst 끝부분 훅
  if (Value *V = foldClampWithNaNFallback(SI, Builder))
    return replaceInstUsesWith(SI, V);

  return nullptr;

3. 왜 이렇게 바꿨나 (근거)

3-1. 왜 이 변환을 하나 — 목적

  • 손으로 쓴 clamp 패턴은 연산 6개(fcmp 3 + select 3)로 길고, 백엔드가 최적화하기 어렵다.
  • llvm.minnum / llvm.maxnum은 LLVM의 표준 정규형이며, 각 타깃 백엔드가 전용 명령 (예: x86 minss/maxss, AArch64 fminnm/fmaxnm)으로 잘 낮춰준다.
  • 즉 정규화 = 후속 최적화·코드 생성 품질 향상.

3-2. 왜 매 단계마다 조건을 이렇게 깐깐하게 검사하나

fold는 "값이 100% 동일할 때만" 바꿔야 한다(안 그러면 컴파일러가 프로그램 의미를 바꿈). 그래서 패턴의 각 부품을 정확히 검사한다:

검사 이유
FCMP_ULT (unordered <) 첫 비교가 "x < LO 또는 x가 NaN"을 잡아야 함. ordered(olt)면 NaN 경로가 빠짐
FCMP_OLT (ordered <) 상한 비교는 NaN을 포함하면 안 됨
FCMP_ORD 하한 분기는 "x가 NaN이 아닐 때"만 LO를 골라야 함
getOperand(0) != X 세 비교가 모두 같은 %x 를 대상으로 해야 함 (다른 값이면 다른 계산)
LowSel->getTrueValue() != Lo 하한 상수와 첫 비교의 LO 상수가 동일 해야 함
Lo/Hi 가 Constant 상수 경계여야 안전하게 min/max로 접힘

3-3. 왜 nsz(no-signed-zeros)를 모든 값-생성 연산에서 요구하나

  • 부호 있는 0(+0.0 vs -0.0) 때문에 원본 select와 minnum/maxnum의 결과가 미세하게 달라질 수 있다.
  • 이 둘이 값-동치가 되려면 값을 만드는 모든 select/call에 nsz가 있어야 한다. (비교(fcmp)에 붙은 nsz는 결과값에 영향 없어 무관.)
  • 그래서 Outer, UpperSel, LowSel, 그리고 새로 만든 minnum/maxnum 모두 nsz를 확인/설정한다.

3-4. 왜 isa<FPMathOperator> 가드를 넣었나 ★ (회귀 테스트로 발견한 버그)

  • 초기 버전은 Outer.hasNoSignedZeros()를 곧바로 호출했다.
  • 그런데 hasNoSignedZeros()는 부동소수점 연산에서만 유효하다(내부에 assert(isa<FPMathOperator>(this))).
  • LLVM에는 정수 select(select i1 %c, i32 %a, i32 %b)가 매우 흔한데, 여기에 호출하면 assertion이 터지며 opt가 크래시(SIGABRT) 한다.
  • 결과: 첫 회귀 테스트에서 select를 쓰는 무관한 테스트 336개가 무더기로 실패.
  • 수정: 패턴 매칭 맨 앞에 if (!isa<FPMathOperator>(&Outer) ...) 가드를 추가해 정수 select는 즉시 return nullptr 하도록 했다. → 336 → 0 실패.

문제와 목표

일반 숫자는 하한과 상한 사이로 제한한다. NaN 입력에는 별도의 fallback 값을 반환한다. 기존 표현은 여러 fcmp와 select가 얽힌 트리다.

목표는 NaN 선택과 범위 제한을 분리하는 것이다. 범위 제한은 llvm.minnum과 llvm.maxnum으로 표현한다.

LLVM
; 구조를 설명하기 위한 요약이다. 실제 적용에는 아래 조건이 필요하다.
%isnan = fcmp uno float %x, %x
%upper = call nsz float @llvm.minnum.f32(float %x, float 1.0)
%clamped = call nsz float @llvm.maxnum.f32(float %upper, float 0.0)
%result = select i1 %isnan, float %fallback, float %clamped

변환 조건

  • 값을 만드는 select에서 필요한 signed-zero 허용 조건을 확인한다.
  • 하한과 상한의 순서를 확인한다.
  • scalar 또는 부동소수점 vector 타입으로 범위를 제한한다.
  • denormal 처리 모드가 변환의 의미를 바꾸는지 확인한다.
  • NaN 입력에서는 fallback이 그대로 선택되어야 한다.

fcmp는 +0과 -0을 같은 값으로 비교한다. 비교 명령의 nsz 여부와 값을 만드는 명령의 nsz 요구를 구분해야 한다.

자료에는 성공한 증명뿐 아니라 실패한 시도와 그 원인도 남아 있다. 형식 검증의 결론은 도구가 모델링한 조건 안에서 읽어야 한다.

자료별 구현 단계

DOCX는 패턴 정의, 선례, 실험, 검증과 로컬 구현 검토를 상세히 다룬다. 수정 DOCX에는 설명 그림과 용어 정리가 추가되었다.

16장 발표자료는 이슈 제안과 별도 실습 브랜치를 구분한다. 18장 발표자료는 darktable 사례와 이후 브랜치의 구현 상태를 추가한다.

Markdown 패치 보고서는 로컬 구현과 회귀 테스트 결과를 설명한다. 각 자료의 숫자와 구현 상태는 해당 버전의 기록이다.

읽을 때 확인할 점로컬 실험, 이슈 등록, 브랜치 구현은 서로 다른 단계다. 이 자료 묶음만으로 최종 업스트림 병합이나 모든 타깃의 성능 개선을 단정하지 않는다.

결과와 남은 문제

단순한 수식 치환을 FP 의미론, 실제 사용 사례, 검증 조건으로 확장한 기록이다. 이후 발견한 타입 크래시와 타깃별 비용 문제는 별도 문서에서 설명한다.

NaN을 별도로 처리해도 minnum·maxnum에 근거 없는 nnan을 붙일 수는 없다. 이 차이가 일부 타깃의 libcall 비용으로 이어질 수 있다.
