실제 출처 — ROCm device-libs

AMD GPU용 수학 함수 라이브러리에서 실제로 등장하는 패턴

ROCm 이란

AMD GPU에서 연산을 돌리기 위한 오픈소스 플랫폼 (NVIDIA의 CUDA에 대응). device-libs는 그 안에서 GPU 커널이 쓰는 수학 함수(로그, 감마함수 등)들을 모아둔 저장소.

실제 등장 위치

// ROCm-Device-Libs, tgammaF.cl (감마 함수 구현) 등
bool isInt = fract(x, &unused) == 0.0f;   // "x가 정수인가?" 를 이렇게 체크

이 코드가 컴파일될 때 fract()가 인라인되면서, 다음 슬라이드의 9개짜리 IR로 펼쳐진다

NaN 과 ±inf 란? / 부동소수점(float)에는 “보통 숫자” 말고도 이런 특수값들이 있다

NaN 과 ±inf 란?

부동소수점(float)에는 “보통 숫자” 말고도 이런 특수값들이 있다

+inf / -inf
NaN

“무한대” 값. 너무 커서 표현 못 하는 수, 또는 1.0 / 0.0 같은 연산의 결과

“Not a Number”. 정의되지 않은 연산의 결과. 어떤 수와 비교해도 참이 안 됨 (자기 자신과 비교해도 거짓)

1.0 / 0.0  =  +inf
inf - inf  =  NaN
NaN == NaN  →  false

→ 그래서 컴퓨터가 “x가 정수인가” 를 판단할 때, 보통 값 말고 이 두 특수값도 따로 챙겨줘야 한다

실제로 펼쳐진 IR / fract(x) == 0 이 컴파일러 내부에서 실제로 만들어내는 코드

실제로 펼쳐진 IR

fract(x) == 0 이 컴파일러 내부에서 실제로 만들어내는 코드

define i1 @src(float %x) {
  %i    = call float @llvm.floor.f32(float %x)         ; floor(x)
  %sub  = fsub nsz float %x, %i                         ; x - floor(x) = 소수부
  %i1   = call nsz float @llvm.minnum.f32(float %sub, float 0x3FEFFFFFE0000000)
                                                         ; 소수부를 1.0 바로 아래로 클램프
  %i2   = fcmp uno float %x, 0.0                        ; x가 NaN인가?
  %cond = select i1 %i2, float %x, float %i1            ; NaN이면 x 그대로, 아니면 클램프값
  %i3   = call float @llvm.fabs.f32(float %x)           ; |x|
  %i4   = fcmp oeq float %i3, 0x7FF0000000000000        ; |x| == +inf ?
  %i5   = fcmp oeq float %cond, 0.0                     ; 소수부가 0인가?
  %cmp  = or i1 %i4, %i5                                ; isinf(x) OR frac==0
  ret i1 %cmp
}

9개 명령어와 trunc(x)==x / trunc(x) == x

9개 명령어와 trunc(x)==x

trunc(x) == x

왜 같은가 — 딱 세 가지 경우만 확인하면 됨

x가 정수(또는 ±inf)면 → 소수부가 0 → 트리는 true, trunc(x)도 x와 같아서 true

x가 정수가 아니면 → 소수부가 0이 아님 → 트리는 false, trunc(x)도 x와 달라서 false

x가 NaN이면 → 양쪽 다 false로 자연스럽게 떨어짐

자동화가 막히는 지점 / 이미 있는 fold는 아주 좁은 모양 하나만 알아본다

자동화가 막히는 지점

이미 있는 fold는 아주 좁은 모양 하나만 알아본다

이미 된 것 (PR #190620)

fcmp oeq floor(x), x   또는   fcmp oeq ceil(x), x   →   fcmp oeq trunc(x), x

딱 이 모양 — “floor/ceil(x)를 x와 바로 비교” 하는 경우만 자동으로 바뀐다

문제 — 우리 코드는 이 모양이 아니다

%sub = fsub nsz x, floor(x) → floor(x) 가 fsub 안에 파묻혀 있음

floor(x)를 곧바로 x와 비교하는 게 아니라, 뺄셈(fsub)·클램프(minnum)·select·or 로 겹겹이 감싸여 있어서 위의 좁은 패턴에 걸리지 않는다

남은 일

fract(x) == 0 전체 트리를 한 번에 인식해서, trunc(x) == x 로 접는 fold를 만드는 것 — 그게 이 이슈(#188035)에서 남은 일이다.

한 줄 정리

명령어 9개짜리 트리를, trunc(x)==x 로 접는다

도착점(floor/ceil → trunc)은 이미 되어 있고, 남은 건 fract(x) == 0 트리 전체를 한 번에 인식해서 접는 것

페이지 배치·기호·도식 확인하기
핵심 원리와 편집 주석

실제 코드와 문제

ROCm device-libs의 감마 함수 구현에는 fract(x) == 0 형태의 정수 판정이 등장한다. 인라인 이후에는 floor, 뺄셈, minnum, 특수값 검사와 선택이 결합된다.

TEXT
복잡한 fract(x) == 0 패턴
          ↓
      trunc(x) == x

여기서 trunc는 부동소수점의 소수 부분을 버리는 연산이다. 정수 타입으로 비트를 자르는 LLVM IR의 trunc 명령과 구분한다.

입력별 의미

  • 유한한 정수 입력에서는 trunc 결과가 입력과 같다.
  • 유한한 비정수 입력에서는 trunc 결과가 입력과 다르다.
  • NaN·무한대는 원래 트리의 특수값 처리와 함께 확인해야 한다.

자료는 특수값 경로를 포함한 전체 IR을 제시한다. 한 부분식만 떼어 일반적인 fract 정의와 같다고 가정하면 안 된다.

기존 fold와 남은 범위

연결된 PR #190620은 이미 더 좁은 패턴을 처리한다. 이슈 #188035의 과제는 복잡한 fract 트리 전체를 인식하는 것이다.

기존 fold가 도착점의 일부를 처리한다는 사실과, 이슈 전체가 해결되었다는 판단은 구분해야 한다.

구현 전 확인할 내용

  1. 실제 라이브러리에서 생성된 IR을 최소화한다.
  2. NaN·무한대·signed zero 입력의 결과를 정리한다.
  3. Alive2가 지원하는 범위에서 변환을 확인한다.
  4. 기존 matcher와 겹치는 부분을 찾는다.
  5. 전체 트리와 부분 패턴의 positive·negative 테스트를 나눈다.
읽을 때 확인할 점제출 자료는 이슈 소개와 설계 분석이다. 완성된 새 패치나 새 성능 측정 결과를 제시한 문서로 읽지 않는다.
