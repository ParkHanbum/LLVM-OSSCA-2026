Closed Good First InstCombine 실습 기록

1. 선택한 이슈

Issue: LLVM Issue #90000

제목: @min(@ctz(x), y) can become @ctz(x | (1 << y))

Issue 링크: https://github.com/llvm/llvm-project/issues/90000

Labels: good first issue , llvm:instcombine , missed-optimization

상태: Closed 해결 PR: #90402 PR 링크: https://github.com/llvm/llvm-project/pull/90402

이 이슈는 ctz 또는 clz로 zero count를 계산한 뒤 min으로 결과의 상한을 제한하는 코드를, 입력의 특 정 bit를 미리 1로 설정한 뒤 ctz 또는 clz만 수행하는 형태로 바꾸는 최적화를 제안한다.

왜 이 이슈가 InstCombine 문제라고 판단했는가?

이 문제는 CFG를 변경하거나 특정 하드웨어의 assembly를 직접 수정하는 문제가 아니다. 다음과 같은 LLVM IR instruction 조합을 더 canonical하고 단순한 IR 형태로 바꾸는 문제다.

cttz/ctlz → umin
or → cttz/ctlz

즉 target-independent한 local IR combine과 canonicalization을 수행하는 InstCombine의 범위에 해 당한다.

실제 코드에서 발생하는 패턴인가?

이슈 작성자는 처음에 u16의 ctz가 특정 bit를 OR한 뒤 tzcnt로 내려가는 assembly를 보고 이론적으 로 아이디어를 얻었다. 이후 benchmark corpus를 검색한 결과 cttz + umin 패턴은 72건과 image-rs, QEMU 사례에서 발견됐지만, ctlz + umin은 해당 benchmark에서는 발견되지 않았다.

Instruction 의미 / llvm.cttz 정수의 오른쪽, 즉 LSB 쪽에서 연속된 0의 개수를 계산 / llvm.ctlz 정수의 왼쪽, 즉 MSB 쪽에서 연속된 0의 개수를 계산

Instruction

의미

llvm.cttz

정수의 오른쪽, 즉 LSB 쪽에서 연속된 0의 개수를 계산

llvm.ctlz

정수의 왼쪽, 즉 MSB 쪽에서 연속된 0의 개수를 계산

llvm.umin

두 정수를 unsigned 값으로 해석해 더 작은 값을 반환

or

두 bit 중 하나라도 1이면 결과 bit를 1로 설정

shl , lshr

OR할 mask의 bit 위치를 계산할 때 사용

cttz : Count Trailing Zeros

cttz는 정수의 오른쪽부터 연속된 0의 수를 센다.

x = 0010 1000
오른쪽에서 0 → 0 → 0 → 1이므로:
cttz(x) = 3

ctlz : Count Leading Zeros

ctlz는 정수의 왼쪽부터 연속된 0의 수를 센다.

x = 0001 0100

왼쪽에서 0이 세 개 나온 뒤 1이 나오므로:

ctlz(x) = 3

원래 패턴

umin(cttz(X), C)
umin(ctlz(X), C)

cttz 또는 ctlz 결과가 C보다 크면 umin이 결과를 C로 제한한다.

기대 패턴

페이지 배치·기호·도식 확인하기

umin(cttz(X), C) / → / cttz(X | (1 << C))

umin(cttz(X), C)
→
cttz(X | (1 << C))
umin(ctlz(X), C)
→
ctlz(X | (MSB >> C))

cttz의 경우 bit C를 미리 1로 설정한다. 그러면 오른쪽에서 0을 세더라도 늦어도 bit C에서 1을 만나므로 결과가 C를 초과할 수 없다.

ctlz의 경우 최상위 bit 하나만 1인 MSB를 C만큼 오른쪽으로 이동한 위치를 설정한다. 그러면 왼쪽에서 0을 셀 때 결과가 C를 초과하지 않는다.

상수 6인 대표 사례

umin(cttz(X), 6)
→
cttz(X | 64)
64 = 1 << 6

i16 의 ctlz 에서는 최상위 bit index가 15이므로:

umin(ctlz(X), 6)
→
ctlz(X | 512)
512 = (1 << 15) >> 6
    = 1 << 9

이슈 원문의 최초 ctlz 식은 (1 << 16) >> 6 을 사용해 bit 10을 설정하는 off-by-one 오류가 있었다. 댓글에서 16비트의 MSB index는 15이므로 (1 << 15) >> 6 이 맞다고 수정됐다.

두 식이 같은 이유

cttz를 예로 들면 두 경우로 나눌 수 있다.

cttz(X) < C 라면 bit C 보다 오른쪽에 이미 1이 있으므로 bit C 를 설정해도 원래 zero count가 바 뀌지 않는다.

페이지 배치·기호·도식 확인하기

cttz(X) >= C 라면 bit C 를 새로 설정했을 때 가장 오른쪽의 1이 bit C 에 생기므로 결과가 정확히 / C / 가 된다.

cttz(X) >= C라면 bit C를 새로 설정했을 때 가장 오른쪽의 1이 bit C에 생기므로 결과가 정확히 C가 된다.

따라서:
cttz(X | (1 << C))
=
umin(cttz(X), C)

가 성립한다. ctlz도 MSB 방향에서 같은 원리가 적용된다.

결과

Transformation seems to be correct!

따라서 scalar i16 , 상수 6, zero-defined cttz 형태에서는 Source를 Target으로 바꾸어도 의미가 보 존됨을 확인했다.

내가 이해한 안전 조건

mask를 만들 때 bit 위치와 정수 비트폭을 올바르게 처리해야 한다. C < bitwidth 이면 해당 위치에 bit를 설정해 bounded zero count를 만든다. C >= bitwidth 이면 zero-count 결과가 원래부터 C 이하이므로 umin 만 제거할 수 있다.

cttz/ctlz 의 is_zero_poison 인자가 true 와 false 인 경우를 모두 고려해야 한다.

OR를 적용한 Target 입력은 특정 bit가 반드시 1이므로 0이 될 수 없다. 이슈 댓글의 Alive2 proof에서는 0 <= C < bitwidth인 변수 상한에 대해서도 수학적으로 변환이 성 립했다. 그러나 변수 상한을 실제 패치에서 지원할지는 의미 보존과 별개로 runtime mask 계산 비용을 고려해야 한다.

Issue 원문의 ctlz 오타

Issue 작성자의 최초 bounded_lzcnt_better 는 (1 << 16) >> 6 을 사용하므로 다음 명령이 생

성된다.

or edi, 1024

그러나 16비트 정수의 최상위 bit index는 15이므로 댓글에서 수정된 올바른 식은 (1 << 15) >> 6 이다.

(1 << 15) >> 6
= 1 << 9
= 512

따라서 수정된 변환에 대응하는 올바른 mask는 512다.

Source Assembly

src:
        or      edi, 65536
        mov     eax, 6
        tzcnt   ecx, edi
        cmp     cx, 6
        cmovb   eax, ecx
        ret

or edi, 65536 은 cttz i16 %x, false 의 zero-input 결과를 16으로 만들기 위한 처리다.

65536 = 1 << 16

x86 코드에서는 32비트 tzcnt를 사용하므로 아무 처리 없이 0을 입력하면 결과가 32가 된다. bit 16을 미 리 설정하면 하위 16비트가 모두 0일 때 결과가 16이 되어 LLVM i16의 zero-defined 의미를 구현할 수 있다.

m_OneUse는 의미 보존 조건이라기보다 수익성 조건이다. 기존 cttz/ctlz가 다른 곳에서도 사용된다면 기존 연산을 제거할 수 없어 or + 새로운 zero-count가 추가되기 때문이다.

실제 mask 생성

cttz :
mask = 1 << C
ctlz :
mask = MSB >> C

C < bitwidth 이면 mask를 OR해 bounded zero count를 생성한다.

umin(cttz(X), C)
→
cttz(X | mask)

C >= bitwidth 이면 zero-count 결과가 이미 C 이하이므로 mask를 추가하지 않고 umin 만 제거한다.

Zero flag 처리

핵심 변환은 원래 is_zero_poison 값 Z 를 새 intrinsic에 그대로 전달한다.

cttz(X, Z)
→
cttz(X | mask, Z)

최종 테스트 결과에서 false가 true로 바뀌는 것은 이 변환이 직접 flag를 변경해서가 아니라, X | mask 가 non-zero임을 다른 InstCombine 로직이 확인해 후속 canonicalization을 수행한 결과다.

리뷰에서 확인한 핵심 쟁점

변수 상한은 수학적으로 변환 가능하지만 runtime mask 계산으로 instruction이 증가할 수 있어 지원하 지 않았다. non-splat vector 지원은 lane별 mask 처리로 구현 복잡도가 크게 증가해 최종 범위에서 제외됐다. Alive2 proof의 assume 조건은 실제 C++ 구현의 적용 조건과 대응해야 한다. PatternMatch는 코드를 짧게 만드는 문법을 넘어 IR 구조와 적용 조건을 선언적으로 표현한다. 더 많은 입력을 지원하는 것보다 수익성, 코드 복잡도, 유지보수성을 고려해 범위를 제한하는 것이 중요하 다.

변환의 의미

cttz(X)는 최하위 비트 쪽의 연속된 0 개수다. 결과를 상수 C 이하로 제한하려면 입력의 bit C를 미리 1로 만들 수 있다.

TEXT
umin(cttz(X), C) → cttz(X | (1 << C))
; 이 식은 C가 유효한 비트 위치인 범위를 설명한다.

원래 zero count가 C보다 작으면 더 낮은 1비트가 결과를 결정한다. 그렇지 않으면 새로 설정한 bit C가 결과를 C로 고정한다.

경계와 적용 조건

  • cttz와 ctlz에는 방향에 맞는 서로 다른 마스크를 사용한다.
  • 상수 C가 0, 마지막 비트, 비트 폭 이상인 경우를 나누어 처리한다.
  • 입력이 0일 때 intrinsic의 zero-undef 조건을 확인한다.
  • 원래 zero count 결과의 one-use 조건을 확인한다.
  • vector의 상수가 uniform splat인지 확인한다.

유효한 비트 위치를 벗어나는 C에는 단순히 1 << C를 만들면 안 된다. 이 경우의 umin 제거 가능성은 별도 조건으로 판단한다.

구현과 분석 순서

대상은 umin과 zero-count intrinsic의 조합이다. 작성자는 InstCombineCalls.cpp의 intrinsic 처리 경로를 예상한 뒤 실제 패치와 비교했다.

  1. 최소 src·tgt IR을 작성한다.
  2. Alive2로 변환 조건을 확인한다.
  3. InstCombine만 실행해 IR 변화가 생기는지 확인한다.
  4. 같은 llc 조건에서 기계어를 비교한다.
  5. 경계값과 적용하면 안 되는 사례를 테스트한다.

근거와 결과의 범위

자료가 인용한 이슈의 코퍼스 조사에는 cttz+umin 사례가 있지만 같은 조사에서 ctlz+umin 사례는 발견되지 않았다. 둘의 실제 사용 빈도가 같다고 가정하지 않는다.

작성자는 비교와 조건부 이동의 제거 가능성을 관찰했다. 정확성, 적용 빈도, 타깃별 비용은 각각 다른 질문이다.
