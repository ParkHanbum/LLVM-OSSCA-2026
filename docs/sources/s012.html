처음 문제

대상 루프는 while (len > 1) len -= 2;다. 부호 없는 len이라면 최종 결과는 짝수에서 0, 홀수에서 1이다.

LLVM이 만든 중간 표현에는 umax(len, 1)과 하위 비트를 지우는 AND가 남았다. 작성자는 이 표현이 왜 원래 값의 짝홀성과 같은지 분석했다.

TEXT
len == (max(len, 1) & -2)
              ↓
       (len & 1) == 0

필요한 비트만 보기

umax(A, C)가 A와 다른 부분이 결과에서 사용하지 않는 낮은 비트에만 있으면 상한 처리를 제거할 수 있다.

필요한 비트 중 가장 낮은 위치를 d라 하자. C.getActiveBits() <= d이면 C는 2^d보다 작다. A가 C보다 작은 경우에도 두 값의 bit d 이상은 모두 0이다.

읽을 때 확인할 점원자료에는 이 경계를 C <= 2^d로 쓴 부분이 있다. active-bits 조건의 정확한 해석은 C < 2^d다. 이 편집본은 경계를 분명히 적고 원자료를 함께 제공한다.

비교 정규화와 사용처

TEXT
(X & C) == X  →  (X & ~C) == 0

위 정규화는 필요한 비트를 직접 비교하는 형태를 만든다. 새 모양은 후속 fold의 조건을 만족할 기회를 늘릴 수 있다.

정규화했다고 언제나 single-use가 되는 것은 아니다. 다른 사용처가 남는지 별도로 확인해야 한다.

3 이상으로 확장한 탐구

작성자는 3씩 빼는 경우를 추가로 관찰하고 umax와 urem이 섞인 식을 분석했다.

TEXT
A - umax(A, K-1) + urem(umax(A, K-1), K)
                      ↓
                  urem(A, K)

K와 A의 범위, 비트 폭, 정수 넘침, 0 나눗셈 조건을 함께 검증해야 한다. 자료의 코드 조각은 이 일반화에 대한 패치 접근안이다.

읽을 때 확인할 점제안한 matcher가 업스트림에 반영되었거나 모든 정수 조건에서 검증되었다는 결론은 자료만으로 확인할 수 없다.
