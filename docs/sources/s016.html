1. #216072 — 이슈와 수학적 근거

출발점은 이슈 #214480의 (X urem Y) == X 비교 최적화였다. 이를 구현한 PR #214933에서 회귀가 발견되어, 값 관계 분석을 보완하는 이슈 #216071과 PR #216072를 별도로 만들었다.

unsigned 나눗셈에서 몫을 Q, 나머지를 R이라 두면:

이 등가식으로 remainder와 dividend의 비교를 X와 Y의 비교로 바꿀 수 있다. Y = 0이면 원본 urem가 UB이므로 별도 nonzero 조건을 추가하지 않았다. 이 변환은 urem에 한정했다.

근거: 출발 이슈 · 수학·UB 검토 [미첨부]

2. 초기 접근: InstCombine에서 비교를 치환

foldICmpBinOp()에서 패턴을 매칭했다. m_c_ICmp로 eq/ne의 양쪽 operand 순서를 처리하고, scalar·vector·remainder extra-use 테스트를 추가했다. Alive2와 관련 InstCombine 테스트는 통과했다.

remainder에 다른 use가 있으면 urem는 남고 compare만 바뀐다. 리뷰의 실제 IR corpus 검사에서 이 경우 후속 umax 최적화가 사라지는 사례가 나왔다.

근거: 초기 구현과 리뷰 [미첨부] · 원래 PR

3. 회귀 원인: branch에서 얻는 관계가 달라졌다

수식의 의미는 유지되지만 LLVM이 사용할 수 있는 관계가 달라졌다. 기존에는 false edge에서 X != R를 직접 알았다. fold 후에는 X u>= Y에서 X != X urem Y를 복구해야 했다.

기존 테스트에는 branch 조건·remainder extra-use·umax가 결합된 이 사례가 없었다. 이 회귀를 막는 분석을 선행 PR #216072로 분리했다.

근거: 회귀 IR 분석 [미첨부] · 분리한 이슈

4. 2차 작업: ValueTracking에 non-equality 추론 추가

첫 보완안은 InstSimplify에서 (X − X%Y) u≥ 1을 직접 매칭하는 것이었다. dtcxzyw가 기존 nonzero 분석 경로를 제안해, ValueTracking::isKnownNonEqual()에 urem 관계를 추가하는 방식으로 바꿨다.

dominating condition만 사용한 버전은 corpus의 X = add nuw A, Y 사례를 놓쳤다. 정의된 add nuw 결과는 Y 이상이므로, 최종 helper는 식 구조를 먼저 확인하고 branch 조건을 확인한다.

isTruePredicate가 UGE를 처리하지 않아 동치인 Y ULE X로 질문한다. 이 helper를 양쪽 operand 순서로 호출하면 기존 분석이 eq/ne, 0·1 비교, umax에 결과를 재사용한다.

테스트확인한 동작
add nuw / branch 조건직접 eq·ne, operand 교환, fixed vector의 구조적 증명, umax 제거
일반 add / 관계 없음 / 다른 divisor증명할 수 없는 입력에서 compare·umax 유지

테스트 초안의 X ≥ Y, R = Z % Y는 negative로 잘못 잡았다. 실제로 R < Y ≤ X이므로 두 값은 다르다. 관계를 보장하지 않는 다른 divisor 사례로 교체했다. 일반 add도 i8에서 250 + 10 = 4로 wrap하므로 nuw 사례와 나눴다.

최종 변경은 ValueTracking +22줄과 회귀 테스트 +412줄이다. branch 추론은 바로 앞 predecessor의 조건에 한정된다. 더 일반적인 지배 조건은 이 구현으로 처리하지 못한다.

5. #218256 — 오류 복구 AST에서의 크래시

modernize-use-noexcept는 예전 dynamic exception specification을 현대적 표현으로 바꾸도록 진단과 fix-it을 만드는 clang-tidy check다. 이슈의 최소 입력은 다음과 같다.

primary template의 T::X는 dependent 상태로 남을 수 있다. 그러나 decltype(f<S>())에서 specialization의 exception specification을 요구하면 아직 S의 정의가 끝나지 않아 사용할 수 없다. Clang은 다음 진단을 낸다.

컴파일 오류 자체는 예상된 결과다. Clang frontend는 오류 뒤에도 추가 진단 등을 위해 recovery AST를 남기며, clang-tidy는 그 AST를 계속 방문한다. 실패한 specialization의 FunctionProtoType에 남은 EST_Unparsed가 이번 크래시의 핵심이다.

작업 기록

시스템 clang-tidy 18에서는 SIGSEGV가 나서 처음에는 source range나 invalid exception type을 의심했다. trunk assertion build와 llvm-symbolizer의 stack을 확보한 뒤 isNothrow 경로로 원인을 정정했다.

근거: 원인 추적 워크노트 [미첨부] · 원 이슈

6. matcher와 예외 명세 상태

function declaration 경로의 matcher는 source에 dynamic exception specification이 있는 선언을 찾는다. isValid()는 선언의 invalid bit만 검사한다.

callback은 semantic type과 source 위치를 각각 얻는다. source spelling에 대한 matching이 성공했다고, query 대상 FunctionProtoType의 exception-spec 상태까지 안전하다고 결론낼 수 없다.

표현여기서의 역할
FunctionProtoType예외 명세 상태를 포함한 함수의 semantic type. isNothrow가 읽는 대상.
TypeLoc / FunctionTypeLoc소스에서 type이 적힌 위치. throw(...)의 수정 범위를 얻는다.
TypeSourceInfosemantic type과 type location 데이터를 연결한다.
CharSourceRangeLexer::makeFileCharRange로 얻는 파일의 교체 가능 범위. invalid이면 fix-it 생성 제한.

기존 guard가 호출하는 helper는 두 상태만 검사했다.

즉 EST_Unparsed는 기존 guard를 통과하지만 canThrow()의 허용된 입력 상태가 아니다. isNothrow()를 호출하기 전에 예외 명세 상태를 확인해야 한다.

8. 표준별 no-crash 테스트

회귀 입력은 의도적으로 compiler error를 발생시킨다. -expect-clang-tidy-error는 진단을 동반한 오류 종료를 기대하도록 하는 옵션이며, 임의의 signal crash를 성공으로 허용하는 옵션이 아니다. 진단 문자열과 순서는 FileCheck로 확인한다.

작업 당시 표준 확장기대 진단
C++11 / C++14primary template의 modernize-use-noexcept warning + f<S>의 exception-spec unavailable error
C++17 / 20 / 23 / 26위 진단 + typed dynamic exception specification 금지 error

새 테스트는 COMMON과 CXX17 suffix로 표준별 출력 차이를 표현한다. CHECK-MESSAGES는 작성자가 직접 쓰며, check_clang_tidy.py는 clang-tidy 실행과 FileCheck 비교를 수행한다. InstCombine의 update_test_checks.py와 역할이 다르다.

urem: 식을 바꾸는 대신 관계를 알리기

초기 접근은 InstCombine에서 비교식을 바꾸는 것이었다. 그러나 분기에서 얻던 값의 관계가 달라져 후속 추론이 약해질 수 있었다.

최종 방향은 isKnownNonEqual에서 구조적인 관계를 알려 주는 것이다. 공통 분석이 필요한 사실을 반환하면 기존 사용처가 그 정보를 사용한다.

자료는 중간 워크노트와 최종 병합 코드의 범위를 구분한다. 이후 추가한 증명과 파일 구성은 공개 리뷰와 병합 코드를 근거로 설명한다.

예외 명세: 조회 전에 상태 확인

소스 위치의 matcher가 성공해도 semantic type의 예외 명세가 완성되었다는 보장은 없다. 실패한 template specialization에는 EST_Unparsed 상태가 남을 수 있다.

CPP
if (FnTy->getExceptionSpecType() == EST_Unparsed ||
    isUnresolvedExceptionSpec(FnTy->getExceptionSpecType()))
  return;

callback은 isNothrow를 호출하기 전에 이 상태를 걸러낸다. 전역 helper의 의미를 바꾸는 대신 기존 guard가 책임지는 경계에 검사를 추가한다.

회귀 테스트와 실행 범위

크래시 입력은 compiler error를 내는 잘못된 코드다. 테스트는 오류 진단을 기대하면서 임의의 signal crash는 허용하지 않아야 한다.

C++11·14와 C++17 이후의 추가 진단을 CHECK suffix로 구분한다. helper 도구가 없는 테스트 환경 실패와 새 CHECK의 오류도 나누어 조사했다.

읽을 때 확인할 점자료에는 수정 후 로컬 전체 suite 재실행은 미완주라고 명시되어 있다. focused test 통과와 최종 CI 통과를 로컬 전체 재검증 완료로 바꾸어 쓰지 않는다.
