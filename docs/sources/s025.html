PR #223246 검토 및 성능 측정 브리핑

측정일: 2026-09-15 · 환경: macOS arm64 · 결과는 이 머신에서 측정한 합성 벤치마크입니다.

결론

멘토님이 제안한 측정은 의미가 있습니다. 새롭게 제거되는 중첩 select/PHI의 문자열 길이 호출에는 큰 국소적 효과가 있고, 문자열 생성과 해시까지 포함한 C++ 합성 작업에서는 실행 시간이 8.8% 감소했습니다. 일반적인 동적 문자열의 strlen을 전부 빠르게 만드는 변경은 아닙니다.

동시에 원본 PR의 기존 테스트 회귀를 발견해 로컬에서 수정했습니다. 원본 PR은 핵심 4개 테스트를 통과했지만 관련 19개 전체 중 8개에서 fixpoint 오류가 났습니다. 수정 후 19개 모두 통과했고, 범위를 넓힌 2,355개 중 2,263개 통과 / 92개 미지원 / 실패 0개입니다.

2. 무엇이 빨라지는가

const char *label = x & 1 ? "ok" : x & 2 ? "missing" : "cancelled";
return strlen(label);

기존에는 문자열 포인터를 고른 뒤 런타임에 문자열을 읽어 길이를 계산합니다. PR은 모든 분기에서 길이를 미리 알 수 있으면 길이 2, 7, 9 자체를 고르게 바꿉니다.

; 이전: 문자열 주소 선택 → strlen
%inner = select i1 %c2, ptr @missing, ptr @cancelled
%p = select i1 %c1, ptr @ok, ptr %inner
%len = call i64 @strlen(ptr %p)

; 이후: 상수 길이 선택
%inner.len = select i1 %c2, i64 7, i64 9
%len = select i1 %c1, i64 2, i64 %inner.len
  • 단순한 두 리터럴 select는 기존에도 최적화됩니다. PR의 새 기여를 보여 주는 대표 예시는 중첩 select와 PHI입니다.
  • PHI는 서로 다른 제어 흐름에서 들어온 값 중 실제 실행 경로의 값을 선택합니다.
  • wcslen에는 모듈의 wchar_size 정보가 필요합니다. 이번 C/C++ frontend가 필요한 정보를 생성합니다.
  • 동적 포인터, 변경 가능한 전역, 가변 offset 등 길이를 결정하지 못하는 값이 있으면 호출을 보존합니다.
  • 구현에는 깊이 16 제한, 순환 감지, 캐시가 있습니다. 제한 밖 구조나 순환 PHI까지 모두 최적화한다는 뜻은 아닙니다.
  • 구현의 진입 조건은 단항 constant-foldable libcall이므로 코드 수준의 영향 범위는 strlen/wcslen 이름만으로 제한되어 있지는 않습니다.

3. 발견한 회귀와 수정

재현

build/benchmarks/pr223246/opt-pr -passes=instcombine -S \
  llvm/test/Transforms/InstCombine/strlen-1.ll -o /dev/null

원본 PR은 test_simplify1에서 did not reach a fixpoint after 1 iterations 오류를 냅니다. 부모 커밋의 opt-base는 같은 기존 테스트를 통과합니다. 기대값을 바꿔야 하는 단순 테스트 차이가 아니라 pass의 실제 오류입니다.

원인

prepareWorklist()에서 ConstantFoldInstruction()이 호출의 반환값을 상수로 바꿉니다. 그런데 선언에 속성이 충분하지 않으면 사용자가 사라진 호출이라도 즉시 죽은 명령으로 판단되지 않습니다. 원래 코드는 이 경우에도 continue해서 호출을 작업 목록에서 누락시켰습니다. 따라서 다음 pass 실행 때 추가 정리가 일어나 fixpoint 검사에 실패했습니다.

strlen/wcslen을 새롭게 상수 접기 가능하게 등록하면서 이 경로가 드러났습니다. visitCallInst()에 있는 사용 중인 호출의 직접 제거만으로는, 그 전에 반환값이 접힌 호출을 처리할 수 없습니다.

수정

실제로 삭제한 명령만 continue하고, 삭제되지 않은 명령은 계속 처리하여 작업 목록에 넣습니다. 호출의 속성 추론과 제거가 같은 pass 실행 안에서 끝나게 합니다. 수정 패치는 worklist-fix.patch [미첨부]에 보관했습니다.

기존 테스트가 회귀를 직접 검출하므로 기대값을 완화하거나 fixpoint 검사를 끄지 않았습니다. 같은 내용을 중복하는 새 테스트 대신 기존 회귀 테스트 전체와 인접 pass 테스트를 실행했습니다.

4. 공정하게 비교한 방법

  1. 같은 PR 커밋과 바로 이전 커밋의 production source로 opt-pr / opt-base를 생성했습니다. 빌드 설정은 같은 Release, assertions OFF, AArch64/X86입니다. 초기 비교는 PR에서 바뀐 두 production 파일만 부모 버전으로 바꾸어 빌드했고, 원래 소스와 빌드를 복구했습니다. 재현 스크립트는 로컬 수정 파일도 포함해 세 파일을 명시적으로 복원합니다.
  2. Homebrew Clang 22.1.8의 동일 frontend로 C/C++를 LLVM IR로 생성했습니다. -O2 -Xclang -disable-llvm-passes로 frontend의 LLVM 최적화를 끕니다.
  3. 각각의 LLVM 24 개발 버전 opt로 전체 default<O2> / default<O3> 파이프라인을 실행했습니다. C++ 추가 실험은 O2입니다.
  4. 동일한 현재 브랜치 llc -O2로 기계어를 생성하고 같은 Clang으로 링크했습니다. 서로 다른 clang 버전끼리 비교한 실험이 아닙니다. 설치된 Clang은 LLVM 24의 새 IR 속성을 읽지 못해 backend에는 저장소에서 빌드한 llc를 사용했습니다.
  5. 전체 최적화 이후 각 함수를 internalize,globaldce로 분리하여 별도 실행 파일을 만들었습니다. 분리 단계는 두 변형에 동일합니다.
  6. 드라이버는 별도 translation unit, LTO 없이 컴파일했습니다. 함수는 noinline이며 입력은 런타임의 4,096개 xorshift 값입니다. 계산 결과를 checksum으로 출력합니다.
  7. 프로세스마다 100,000회 warmup 후 20,000,000회 측정, 변형 순서를 고정 seed로 섞어 15회 반복했습니다. C++ 메시지 생성은 회당 비용이 커 2,000,000회씩 측정했습니다.
  8. 모든 측정의 checksum을 Python으로 따로 계산한 기대값과 대조했습니다. 단순히 두 바이너리의 값이 같다는 검사에 그치지 않았습니다.
  9. 빌드와 대규모 테스트를 시간 측정 중에 함께 실행하지 않았습니다. 다만 CPU 고정·클록 고정·다른 앱 종료는 하지 않았습니다.

호스트는 opt --version에서 apple-m1로 보고되는 macOS arm64입니다. 시간은 드라이버 루프와 함수 호출 비용을 포함한 회당 ns의 15회 중앙값입니다. 원본 PR과 수정 버전의 최적화 IR이 같으므로 아래 성능은 로컬 회귀 수정에도 동일한 생성 코드를 나타냅니다.

전체 앱의 최적화 빌드 두 개를 비교하거나 LLVM 소스 전체의 컴파일 시간을 측정한 결과는 아닙니다. libc++와 OS libc는 시스템에 설치된 동일 버전을 사용했습니다.

O2와 O3에서 같은 호출 제거 양상이 나타났습니다. 새로 사라진 정적 길이 호출은 nested, status, wide, long_nested 각각 1개, log_size의 2개 중 1개입니다. C++ 함수 본문에서는 cpp_view, cpp_message의 prefix 호출이 각각 1개에서 0개가 됩니다. 호출 수 자료는 static.json [미첨부], C++ static.json [미첨부]에 있습니다.

8. 측정 중 발견한 배치 효과

처음 모든 kernel을 같은 실행 파일에 넣었을 때, 코드는 같은 동적 대조군이 PR에서 약 25% 느려졌습니다. 이 숫자를 PR의 알고리즘 회귀라고 단정하지 않았습니다. 함수별 어셈블리는 같았고, 각 kernel을 분리한 재측정에서는 차이가 사실상 사라졌습니다.

따라서 코드·상수 배치 등 측정 맥락의 영향으로 해석했습니다. 구체적인 마이크로아키텍처 원인을 확정한 것은 아닙니다. 최초 로그와 원시 데이터도 raw.csv [미첨부], summary.json [미첨부]에 남겼고, 최종 발표에는 isolated/ 결과를 사용합니다. 로그 길이 계산 결과 역시 최초 32% 대신 최종 약 20%를 사용합니다.

9. 발표에서 말할 수 있는 것과 한계

  • 말할 수 있음: 같은 소스·같은 파이프라인에서 PR 하나로 호출이 제거되고, 해당 경로에서 실행 시간이 줄어듭니다.
  • 말할 수 있음: C++ string_view 사례 4.46배, 문자열 생성·append·해시 합성 작업의 시간 8.8% 감소를 관측했습니다.
  • 말할 수 없음: LLVM으로 컴파일한 일반 프로그램 전체가 4~11배 빨라진다는 주장.
  • 말할 수 없음: strlen을 많이 호출하는 모든 프로그램이 빨라진다는 주장. 이 PR은 상수 선택 패턴의 빈도와 실행 비중에 좌우됩니다.
  • 아직 측정하지 않은 것: 실제 서비스/오픈소스 앱 전체 처리량, Linux/glibc 및 x86-64, 컴파일 시간 변화, 모든 LLVM 프로젝트의 전체 테스트.
  • JSON에는 반복 쌍을 bootstrap한 95% 구간도 있습니다. 이 구간은 이 실험의 반복 변동만 나타내며 다른 기기나 실제 앱에 대한 보장을 뜻하지 않습니다.

예를 들어 이 패턴이 원래 총 실행 시간의 1%이고 그 구간이 4.1배 빨라져도, 전체 배속은 1 / (0.99 + 0.01 / 4.1)로 약 1.008배입니다. 따라서 opt-benchmark에서 변화가 작더라도 해당 최적화의 가치와 모순되지 않습니다.

핵심 원리와 편집 주석

어떤 호출을 없애는가

후보 문자열이 모두 상수면 각 후보의 길이를 컴파일할 때 구할 수 있다. 실행 중에는 문자열을 스캔하는 대신 길이 값 자체를 선택한다.

LLVM
; Before: 주소를 선택한 뒤 길이를 계산한다.
%inner = select i1 %c2, ptr @missing, ptr @cancelled
%p = select i1 %c1, ptr @ok, ptr %inner
%len = call i64 @strlen(ptr %p)

; After: 이미 아는 길이를 선택한다.
%inner.len = select i1 %c2, i64 7, i64 9
%len = select i1 %c1, i64 2, i64 %inner.len

단순한 두 리터럴의 select는 기존에도 최적화된다. 이 자료는 중첩 select와 PHI가 새로 처리되는 예제를 구분한다.

구현과 보존 조건

상수 문자열의 평가는 ConstantFolding에서 수행한다. InstCombine은 select·PHI 입력을 따라 결과를 구성한다. strlen 전용 예외 처리보다 기존 상수 접기 체계를 사용하는 설계다.

  • 길이를 알 수 없는 동적 입력이 있으면 호출을 유지한다.
  • 변경 가능한 전역 문자열은 상수 문자열로 가정하지 않는다.
  • 순환을 감지하고 탐색 깊이를 제한한다.
  • 평가 결과를 캐시해 중복 탐색을 줄인다.
  • wcslen에는 필요한 wchar 크기 정보가 있어야 한다.
  • musttail의 직접 반환 조건을 보존한다.

서로 다른 오류의 수정

자료는 Archer의 musttail 크래시 보고와 별도로 발견한 fixpoint 회귀를 구분한다. 핵심 사례 몇 개만 통과한 상태에서도 인접 테스트는 실패할 수 있었다.

호출 결과를 접은 뒤 남은 호출을 작업 목록에서 계속 처리하도록 수정했다. 자료는 19개 관련 테스트 통과와 확장 검증 2,263개 통과·92개 미지원을 기록한다.

8개 테스트 실패는 같은 fixpoint 문제를 검출한 것이다. 이를 독립적인 버그 8개로 세지 않는다. 초기 Markdown의 로컬 수정 상태와 후속 발표의 브랜치 반영 상태도 구분한다.

측정 방법

자료의 측정일은 2026년 9월 15일이다. macOS arm64에서 같은 frontend IR, 부모·PR opt, 같은 llc를 사용했다. O2와 O3는 전체 최적화 파이프라인으로 비교했다.

  • 10만 회 준비 실행 뒤 15회 측정의 중앙값을 사용했다.
  • 실행 순서를 무작위화했다.
  • 런타임 입력과 독립적으로 계산한 checksum을 사용했다.
  • 함수별 실행 파일과 별도 드라이버를 사용했다.
  • LTO를 사용하지 않고 noinline 조건을 유지했다.

측정과 자료의 한계

처음 한 실행 파일에 모은 측정에서는 같은 기계어의 대조군도 느려졌다. 함수를 분리해 다시 측정하자 차이가 줄었다. 작성자는 배치 효과의 원인을 확정하지 않고 최종 발표에 분리 측정값을 사용했다.

벤치마크 원시값과 스크립트의 상대 링크는 첨부 자료에 없는 파일을 가리킨다. 이 사이트는 그 파일을 제공한다고 표시하지 않는다. PR의 현재 상태도 원자료 작성 시점과 구분한다.
